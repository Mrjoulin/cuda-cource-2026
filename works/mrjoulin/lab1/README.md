# Lab 1: Vector Operations and Activations — Векторные операции и активации

## Описание

Реализованы собственные CUDA-ядра для трёх поэлементных операций над векторами `float`:

- `add`: `c[i] = a[i] + b[i]`;
- `saxpy`: `y[i] = alpha * x[i] + y[i]`;
- `relu`: `y[i] = max(0.0f, x[i])`.

Для каждой операции реализованы два варианта доступа к глобальной памяти:

- **coalesced** — последовательные треды в warp читают/пишут последовательные элементы массива;
- **noncoalesced** — каждый тред обрабатывает сплошной непрерывный фрагмент из `64` элементов, поэтому соседние треды обращаются к далёким адресам с шагом `64 * sizeof(float)`, нарушая коалесцентность.

Программа читает векторы из входного файла, выполняет все три операции на GPU в выбранном режиме, сверяет результаты с эталоном на CPU, измеряет время и пишет результаты в файл `--output`.

## Окружение

- **GPU:** Quadro RTX 6000, compute capability 7.5, 24 GiB

## Компиляция

Из каталога лабораторной:

```bash

cmake --build build --target submission
```

## Запуск

```bash
./build/submission --help
./build/submission --input data/example.txt --output result.txt
./build/submission --input data/example.txt --output result.txt --mode noncoalesced
```

Аргументы `--input` и `--output` обязательны, `--mode` необязателен (по умолчанию `coalesced`).

Формат входного файла (`data/example.txt`): первая строка `N alpha`, далее ровно `N` строк с парами `x y`. Файл `data/example.txt` содержит открытый пример из задания:

```text
3 0.5
-3 2
1 -5
4 0.5
```

Результат записывается в `--output`: одна строка на пару входов в порядке `add saxpy relu`. Для примера выше:

```text
-1 0.5 0
-4 -4.5 1
4.5 2.5 4
```

Логи и таблицы замеров выводятся в `stdout`, сообщения об ошибках — в `stderr`. Коды возврата: `0` — успех, `2` — неверные аргументы или входные данные, `1` — ошибка выполнения (в том числе невозможность записать результат).

## Реализация

- `include/kernels.h` — объявления операций и режимов доступа.
- `src/kernels.cu` — шесть ядер (coalesced/noncoalesced × add/saxpy/relu) и общий запускатель `LaunchVectorOp`.
- `include/config.h` / `src/config.cpp` — разбор аргументов командной строки и справка `--help`.
- `src/main.cu` — чтение входа, валидация на малых размерах, проверка входных данных, бенчмарк с CUDA events, запись результата.

Распределение элементов по тредам:

- **coalesced:** `idx = blockIdx.x * blockDim.x + threadIdx.x`, шаг `gridDim.x * blockDim.x`, проверка `idx < n`;
- **noncoalesced:** каждый тред получает фиксированный чанк `chunk_size = 64` элементов, начиная с `tid * chunk_size`, граница обрезается до `n`. Размер сетки выбирается как `(ceil(n / chunk_size) + block - 1) / block`.

SAXPY выполняется in-place: буфер-приёмник предварительно заполняется исходным `y`, поэтому эталон и ядро получают одинаковые входы. Границы массива проверяются в обоих режимах; пустой вход (`N = 0`) отклоняется с сообщением и кодом `2`. Все вызовы CUDA обёрнуты макросами `CUDA_CHECK` / `CUDA_CHECK_KERNEL`, память освобождается.

## Проверка корректности

Эталон — последовательная реализация на CPU с теми же формулами. Ядра проверялись на детерминированных псевдослучайных входах (они покрывают нули и значения разных знаков) на размерах `1, 2, 63, 64, 65, 255, 256, 257, 1023, 1024, 1025` для всех трёх операций в обоих режимах. Допуск на несовпадение — `1e-5`.

| Режим | Проверенные размеры | Операции | Максимальная ошибка | Несовпадений (>1e-5) |
|---|---|---|---|---|
| coalesced | 1–1025 (см. выше) | add, saxpy, relu | 0.00e+00 | 0 |
| noncoalesced | 1–1025 (см. выше) | add, saxpy, relu | 0.00e+00 | 0 |

Кроме того, перед записью файла-результата программа сверяет с эталоном итоговые векторы на загруженном входе: для массива `n = 16 777 216` в обоих режимах максимальная ошибка `0`, несовпадений нет.

## Результаты

Замеры выполнялись с помощью CUDA events, синхронизация через `cudaEventSynchronize`. После двух разогревочных прогонов берётся медиана `20` повторений. Время полного цикла включает H2D-копии, ядро и D2H-копию, но **не включает** однократное выделение памяти.

Вход: `16 777 216` пар (`64 MiB` на вектор), `alpha = 2.0`, значения из `[-1, 1]` по схеме из раздела «Воспроизводимость».

### Основные замеры при block_size = 256

| Режим | Операция | H2D, мс | Ядро, мс | D2H, мс | Полный цикл, мс |
|---|---|---|---|---|---|
| coalesced | add | 29.00 | 0.36 | 15.19 | 44.58 |
| coalesced | saxpy | 28.91 | 0.36 | 15.06 | 44.28 |
| coalesced | relu | 13.89 | 0.25 | 14.88 | 29.03 |
| noncoalesced | add | 28.91 | 8.59 | 13.77 | 51.34 |
| noncoalesced | saxpy | 29.07 | 7.55 | 13.82 | 50.48 |
| noncoalesced | relu | 14.52 | 7.30 | 13.80 | 35.54 |

### Влияние размера блока (время ядра, мс)

| Режим | Операция | 64 | 128 | 256 | 512 | 1024 |
|---|---|---|---|---|---|---|
| coalesced | add | 0.352 | 0.353 | 0.356 | 0.357 | 0.358 |
| coalesced | saxpy | 0.352 | 0.353 | 0.356 | 0.356 | 0.357 |
| coalesced | relu | 0.245 | 0.242 | 0.246 | 0.243 | 0.247 |
| noncoalesced | add | 8.659 | 8.589 | 8.589 | 8.725 | 8.507 |
| noncoalesced | saxpy | 7.615 | 7.624 | 7.553 | 7.807 | 7.628 |
| noncoalesced | relu | 7.346 | 7.323 | 7.296 | 7.367 | 7.103 |

Время выделения памяти замеряется отдельно и в полный цикл не входит; в большинстве прогонов оно составляет `0.3–0.7 мс`.

## Выводы

1. **Коалесцентный доступ значительно быстрее.** При `block_size = 256` ядро `add` ускоряется с `8.59 мс` до `0.36 мс` (≈24×), `relu` — с `7.30 мс` до `0.25 мс` (≈29×). Это соответствует ожидаемому эффекту: warp в coalesced-варианте выполняет один широкий запрос к памяти, а в noncoalesced — множество разрозненных.
2. **Размер блока почти не влияет на ядро.** Для memory-bound операций с таким массивом основным ограничением является пропускная способность памяти, а не occupancy или число блоков. Разброс времени ядра в пределах `±3%` подтверждает это.
3. **Передачи данных дороже вычислений.** Даже в coalesced-режиме H2D+D2H занимают `≈43–44 мс` для add/saxpy (два входных вектора) и `≈29 мс` для relu (один), тогда как само ядро — менее `0.4 мс`. Полезная работа составляет менее `1%` полного цикла.
4. **Накладные расходы GPU окупаются только при достаточном объёме вычислений.** На массиве `64 MiB` переносы доминируют; ускорение ядра за счёт coalescing снижает полный цикл, например для `relu`, на `≈18%`, потому что основное время уходит на PCIe-копии.
5. **Проверка границ работает корректно:** размеры меньше блока и не кратные блоку обрабатываются без ошибок; пустой вход отклоняется с понятным сообщением и кодом `2`.
