# Lab 2: Matrix Multiplication — Матричное умножение

## Описание

Программа считает `C = A * B` для `float`-матриц: `A` размера `M×K`, `B` размера `K×N`, `C` размера `M×N`. Матрицы хранятся по строкам (row-major).

Свои реализации:

- `naive`: один поток считает один элемент `C`, все операнды читаются из global memory;
- `tiled`: блок потоков кооперативно грузит тайлы `A` и `B` в shared memory и считает по ним частичные суммы. Размер тайла 8, 16 или 32 (по умолчанию 16). Размеры `M`, `K`, `N` не обязаны делиться на тайл.

Библиотечные функции используются только как эталон и ориентир по скорости:

- `cublasSgemm` в режиме `CUBLAS_PEDANTIC_MATH`: чистый FP32, без TF32 и других сокращений. Доступен как `--mode cublas`;
- `cublasDgemm` на тех же входных значениях, переведённых в `double`. С ним сравниваются результаты в проверке корректности.

Кроме обязательного `submission` собирается второй файл `bench`. Он нужен для отчёта: проверка корректности, замеры времени, тест bank conflicts. Подробности в разделе «Запуск».

### Naive

Поток `(row, col)` идёт по строке `A` и столбцу `B` и накапливает сумму в регистре. Блок 16×16, потоки warp-а лежат в одной строке `C`. Чтение `B` по соседним столбцам коалесцировано, чтение `A` у всех потоков warp-а одно и то же (broadcast). Всего ядро делает `2·M·N·K` обращений к global memory. Часть из них перехватывают L1 и L2.

### Tiled

Блок `T×T` потоков считает тайл `C` размером `T×T`. Матрицы пробегаются по `K` шагами по `T`:

```text
шаг t = 0 .. ceil(K / T) - 1

        B (K×N)                     C (M×N)
      ┌──────────────┐           ┌──────────────┐
      │  .  .  .  .  │           │              │
      │ [tile B(t)]  │ T строк   │      [C]     │ T×T на блок
      │  .  .  .  .  │           │              │
      └──────────────┘           └──────────────┘
  A (M×K)
  ┌───────────────────┐
  │ [tile A(t)]       │ T строк
  └───────────────────┘

tile A(t): строки блока, столбцы t*T .. t*T+T-1
tile B(t): строки t*T .. t*T+T-1, столбцы блока
```

За один шаг:

1. Каждый поток кладёт один элемент `A` и один элемент `B` в `tileA[ty][tx]` и `tileB[ty][tx]`. Если элемент выходит за матрицу, пишется 0. Нулевые элементы не меняют сумму, поэтому размеры не обязаны делиться на тайл.
2. `__syncthreads()`: пока все потоки не закончили загрузку, читать тайлы нельзя.
3. Поток делает `T` умножений с накоплением: `acc += tileA[ty][i] * tileB[i][tx]`.
4. Второй `__syncthreads()`: пока самый медленный поток не дочитал тайлы, следующий шаг не может их перезаписать.

Потоки за границей `C` не выходят из ядра раньше времени, иначе они пропустят `__syncthreads()` и блок зависнет или даст неверный результат. Условие `row < m && col < n` стоит только перед записью результата.

Данные переиспользуются так: каждый загруженный элемент `A` читается `T` потоками (всей строкой тайла `C`), каждый элемент `B` тоже `T` потоками. Обращений к global memory становится в `T` раз меньше, чем у `naive` (без учёта кэшей).

### Ресурсы ядер

Значения взяты из `cudaFuncGetAttributes` (`bench info`):

| Ядро | Потоков в блоке | Регистров на поток | Static shared memory, байт |
| --- | --- | --- | --- |
| naive16 | 256 | 50 | 0 |
| tiled8 | 64 | 42 | 512 |
| tiled16 | 256 | 40 | 2048 |
| tiled32 | 1024 | 44 | 8192 |
| tiled32pad | 1024 | 36 | 8448 |

Shared memory считается как `2·T·T·4` байт (`2·T·(T+1)·4` с padding). Ядро `tiled32` занимает максимум 1024 потока на SM, то есть на каждом SM помещается один такой блок.

### cuBLAS и порядок хранения

cuBLAS хранит матрицы по столбцам. Строковая матрица, прочитанная как столбцовая, оказывается транспонированной. Поэтому `C = A·B` в row-major вычисляется как `Cᵀ = Bᵀ·Aᵀ` в column-major: в `cublasSgemm` передаются `B`, затем `A`, а `M` и `N` меняются местами. Копировать или транспонировать данные не нужно.

## Проверка корректности

Эталон: `cublasDgemm` на входах, переведённых из FP32 в FP64. Допуск для элемента `C_ij` считается по формуле из задания:

```text
bound_ij = (gamma(2K, u32) + gamma(K, u64)) * S_ij
S_ij     = sum_k |A_ik * B_kj|        (вычисляется тем же cublasDgemm от |A| и |B|)
gamma(q, u) = q*u / (1 - q*u),  u32 = 2^-24,  u64 = 2^-53
```

Первое слагаемое ограничивает ошибку FP32-результата, второе — ошибку самого FP64-эталона. Библиотечный FP32-matmul (`cublas`) проверяется тем же способом, как ещё один вариант. Входы: `mt19937`, seed 2026, равномерно на `[-1, 1]`. Кроме них для каждой формы есть вариант с целыми числами от -3 до 3. В нём все произведения и суммы точно представимы в FP32, поэтому результат должен совпасть с эталоном без единой ошибки.

Проверено 13 форм, по 6 реализаций и 2 типа данных на форму (156 прогонов): `1×1×1`, `2×3×2`, `1×257×1`, `257×1×129`, `16×16×16`, `31×33×35`, `32×32×32`, `33×33×33`, `64×17×95`, `127×65×257`, `256×256×256`, `300×500×200`, `1000×1000×1000`. Все прошли, `failures: 0`. Выдержка (полный вывод получается командой `./build/bench check`):

### Bank conflicts

В основном GEMM конфликтов банков нет, поэтому сделан отдельный тест (`bench banks`). Блок из 256 потоков читает из shared memory слово `lane * stride + c`, где `lane` номер потока в warp-е, `c` меняется от итерации к итерации. Банк слова равен `слово mod 32`. Потоки warp-а попадают в один банк, если `lane * stride` совпадают по модулю 32, а таких потоков `gcd(stride, 32)`. При `stride = 33` номер банка равен `(lane + c) mod 32`, и все 32 потока обращаются к разным банкам. Это и есть padding: ряд из 33 слов вместо 32 сдвигает каждую следующую строку на один банк. Для запуска 256 блоков × 256 потоков и 16384 чтения на поток (медиана 10 запусков):

| Stride | Потоков на банк | Время, мс | Относительно stride 1 |
| --- | --- | --- | --- |
| 1 | 1 | 0.545 | 1.00× |
| 2 | 2 | 1.079 | 1.98× |
| 4 | 4 | 2.150 | 3.94× |
| 8 | 8 | 4.292 | 7.87× |
| 16 | 16 | 8.542 | 15.66× |
| 32 | 32 | 17.080 | 31.32× |
| 33 (padding) | 1 | 0.541 | 0.99× |

Время растёт почти линейно с числом потоков на банк: обращение warp-а разбивается на столько последовательных транзакций. Nsight Compute подтверждает причину (счётчики `l1tex__data_bank_conflicts_pipe_lsu_mem_shared_op_ld` и `l1tex__data_pipe_lsu_wavefronts_mem_shared_op_ld`, один запуск ядра):

| Ядро | Конфликты банков | Wavefronts загрузок shared memory |
| --- | --- | --- |
| тест, stride 1 | 0 | 33 554 432 |
| тест, stride 32 | 1 040 187 392 | 1 073 741 824 (в 32 раза больше) |
| тест, stride 33 | 0 | 33 554 432 |
| GEMM tiled32, 1024³ | 0 | 50 331 648 |
| GEMM tiled32 + padding, 1024³ | 0 | 67 108 864 |

### Padding в GEMM

В `tiled` обращения `tileA[ty][i]` (все потоки warp-а читают одно слово, broadcast) и `tileB[i][tx]` (соседние потоки читают соседние слова) конфликтов банков не создают, и счётчик это подтверждает. Padding здесь ничего не исправляет, а время ядра растёт на 26-31% (`tiled32` против `tiled32 + padding`, например 7.56 против 9.55 мс на 2048³).

Причину показывает дизассемблер (`cuobjdump -sass`). Без padding строка `tileA` лежит с шагом 32 слова, адрес выровнен, и компилятор читает её четвёрками (`LDS.128`): в `tiled32` 8 команд `LDS.128` и 32 скалярные `LDS`. С padding шаг строки 33 слова, выравнивания по 16 байт нет, и остаются 64 скалярные `LDS`, ни одной `LDS.128`. Nsight Compute показывает ту же разницу как рост числа wavefronts на 33% (67.1 млн против 50.3 млн). Конфликтов в обоих вариантах нет.

## Выводы

1. Tiled быстрее naive за счёт сокращения обращений к global memory. На больших формах `tiled32` быстрее `naive16` в 1.77 раза (7.56 против 13.37 мс на 2048³), `tiled16` в 1.57 раза. Выигрыш растёт вместе с тайлом, потому что каждый элемент, загруженный в shared memory, используется `T` раз. У `naive` L1/L2 уже частично берут на себя переиспользование, поэтому выигрыш не равен `T`.
2. Тайл 8 не дал ускорения: `tiled8` на уровне `naive16`. Переиспользование всего в 8 раз, блок из 64 потоков и два `__syncthreads()` на каждые 8 умножений. Я не профилировал это ядро отдельно, поэтому причина остаётся предположением. Тайлы 16 и 32 заметно лучше.
3. Тайл 32 не выигрывает всегда. На малых формах (`65×1000×257`) `tiled32` в два раза медленнее `naive16`: у такой формы всего 27 блоков по 1024 потока на 72 SM, GPU недозагружен, а `naive` запускает 85 блоков. На самых малых формах (`128³`, `127×65×257`) ядра работают около 0.01 мс, и время в основном состоит из накладных расходов запуска.
4. До cuBLAS далеко: наш лучший вариант `tiled32` даёт 2270 GFLOP/s, cuBLAS 13-15 TFLOP/s на больших матрицах, то есть в 5.7-6.6 раза быстрее (60.6 против 10.6 мс на 4096³). По числу ядер и частоте оценка пика FP32 около 16-18 TFLOP/s, cuBLAS подбирается к нему вплотную, а мы используем примерно 13-14%. На каждое умножение с накоплением у нашего ядра приходится две загрузки из shared memory (`tileA` и `tileB`), поэтому скорость, скорее всего, ограничена пропускной способностью shared memory (профилировщиком я это не проверял). Библиотечные ядра, по общеизвестной схеме, считают в каждом потоке сразу несколько элементов `C`, держат операнды в регистрах, используют широкие загрузки и перекрывают загрузку следующего тайла с вычислением. Эти приёмы я не воспроизводил и не профилировал.
5. Padding не обязан ускорять GEMM. Конфликты банков реальны (тест: до 31 раза медленнее при `stride = 32`, `stride = 33` их убирает), но в нашем GEMM их нет, и padding только отключает векторные загрузки `LDS.128`. Он нужен там, где потоки warp-а читают столбец тайла, например при транспонировании.
6. Передачи данных дороже ядра на малых матрицах. На `512³` ядро занимает 15% цикла, а на `4096³` уже 60%. Для одного небольшого умножения без переиспользования данных на GPU копирование через PCIe съедает выигрыш. Выделение памяти (0.2-0.3 мс) заметно только на малых формах.
7. Ограничения: ядра не используют регистровые блоки и двойную буферизацию, тайлы фиксированы 8/16/32 и квадратные, индексы внутри ядер считаются в `size_t`, но размерность `M` ограничена числом блоков по `grid.y` (65535 блоков, при тайле 16 это `M ≤ 1 048 560`).

## Воспроизводимость

### Данные

Для `bench` входы генерируются в программе: `mt19937`, seed 2026 для `A` и 2027 для `B` (при проверке корректности seed сдвигается на каждую форму), равномерно на `[-1, 1]`, целочисленный вариант от -3 до 3. Для `submission` нужен текстовый файл в формате из раздела «Запуск». Небольшой пример из задания лежит в `data/example.txt`, ожидаемый ответ в `data/example_expected.txt`. Большие входы `tests/check_cli.py` создаёт сам (NumPy, seed 2026) и пишет во временный каталог.

### Полный запуск

От чистой сборки до всех результатов отчёта:

```bash
cd works/mrjoulin/lab2
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --target submission bench

# пример из задания: три режима должны дать data/example_expected.txt
for m in naive tiled cublas; do
  ./build/submission --input data/example.txt --output results/ex_$m.txt --mode $m
  diff results/ex_$m.txt data/example_expected.txt && echo "$m ok"
done

# корректность
./build/bench check
python3 tests/check_cli.py

# замеры
./build/bench info
./build/bench time
./build/bench time --shapes 128,256,127x65x257,65x1000x257
./build/bench time --shapes 2048 --repeats 20
./build/bench transfer --shapes 512,1024,2048,4096
./build/bench banks
```

Профиль bank conflicts (Nsight Compute, номер запуска ядра выбирается через `--launch-skip`: каждый stride запускает тест 13 раз):

```bash
M=l1tex__data_bank_conflicts_pipe_lsu_mem_shared_op_ld.sum,l1tex__data_pipe_lsu_wavefronts_mem_shared_op_ld.sum
ncu --metrics $M -k regex:bankTest --launch-skip 65 --launch-count 1 ./build/bench banks
ncu --metrics $M -k regex:matmulTiled --launch-skip 26 --launch-count 1 ./build/bench time --shapes 1024
```

Команды для `tests/check_cli.py` нужны NumPy и собранный `build/submission`.
